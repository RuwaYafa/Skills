# Evidence Bank Schema

Use this structure for each material claim.

| Field | Meaning |
|---|---|
| Claim | Concise factual or synthesized statement |
| Category | education, research, publication, project, data leadership, teaching, technical skill, service, future agenda, target alignment |
| Source | file title, DOI, official page, profile URL, repository, or user confirmation |
| Date/period | year or range if supported |
| Evidence level | A, B, C, or D |
| Professor-facing? | yes / conditional / no |
| Notes | caveat, wording restriction, or status |

## Evidence levels

### A — Documented fact
Directly supported by an uploaded primary source, publication metadata, official institutional page, or DOI record.

Use confidently, preserving scope and status.

### B — Public-profile confirmation
Supported by a public academic/professional profile such as ORCID, Google Scholar, GitHub, LinkedIn, or a lab profile.

Use when the profile is attributable to the user. Prefer A when both exist.

### C — Evidence-based synthesis
A defensible interpretation created by connecting multiple A/B facts, such as a research trajectory or a recurring methodological strength.

Use with measured language: "her work has increasingly focused on...", "the trajectory suggests...", "this experience supports...". Do not present synthesis as a quoted claim or formal title.

### D — Requires confirmation
Plausible but not fully supported: exact role in a multi-author paper, unpublished project status, specific software proficiency level, target-supervisor availability, transfer rationale, or future commitment.

Ask or qualify before using in professor-facing materials.

## Reconciliation rules

- Prefer the newest user-supplied CV/proposal over an older bundled summary.
- If two sources conflict, retain both in notes and ask the user when the difference affects the output.
- Do not silently "correct" source content.
- Preserve exact publication year, venue, title, and authorship order where available.
- Treat proposal objectives, methodology, planned metrics, and future directions as planned work unless the user supplies evidence of implementation/results.
- Treat a GitHub repository as evidence of a public artifact, not automatically as evidence of scientific validation or publication.
- Treat teaching-course names and institutional roles exactly as the source states unless the user confirms an updated title.

## Privacy filter

Default professor-facing exclusions:
- date/place of birth;
- marital status;
- full home address;
- personal mobile numbers;
- unrelated personal details.

Include contact information only when the user explicitly asks for a full CV/contact block.
